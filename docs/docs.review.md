### 5つの単位

| 用語 | 境界 | 責務 | 混同しやすい概念との違い |
| --- | --- | --- | --- |
| Scaffold | Screen Boundary | 画面構造と画面状態 | Flutter の `Scaffold` ウィジェットとは別概念 |
| Bridge | Coordination Boundary | 複数Islandの協調 | GoF の Bridge パターンとは別概念 |
| Island | Feature Boundary | 機能とその状態 | Islands Architecture の island とは目的が異なる |
| Component | Interaction Boundary | 操作と振る舞い(**自分で状態を持つ**) | 一般語の「コンポーネント」とは別 |
| Part | Presentation Boundary | 表現(**状態を持たない**) | Atomic Design の Atom とは分解基準が異なる |

### Component と Part の判定基準(2026-08-10 にユーザーが変更)

**基準 = その要素が自分で状態を持つか。持てば `Component`、持たなければ `Part`。**
代表例は `Button`(押下状態を持つ → `Component`)と `Card`(何も持たない → `Part`)。

**これは素材(`UI Boundary Architecture.md`)の記述を反転させている。** 素材では次のように書かれていた。

> ただし、「内部に状態変数が存在するか」だけでComponentを判定するわけではありません。
> アニメーションやキャッシュなどの実装上の状態ではなく、**UIとして意味のある振る舞いを提供するか**を基準にします。
> そのため、`Part = Stateless` ではなく、`Part = Presentation` と考えます。

新しい基準では `Part = Stateless` が成り立つ。アニメーション進行度・読み込み状態・レイアウトキャッシュも状態に数え、例外を作らない。
例外を設けない理由は、**例外があると基準そのものが議論の対象になる**ため(「これは実装上の都合か、ユーザーから見た振る舞いか」という判定不能な問いが発生する)。

`Part` に留めたい要素に状態が必要になった場合は、状態を外へ出して受け取る形にする。分類は設計の選択として扱う。

**素材と完成版はこの点で食い違っている。** 素材を参照するときは注意する。

### Atomic Design との関係(2026-08-10 にユーザーが2段階で提案)

**第1段階 — 立っている場所の違い。**

| | 立っている場所 | 答えようとしている問い |
| --- | --- | --- |
| Atomic Design | コンポーネントライブラリ | どのアプリでも使える部品を、どう組み立てて揃えるか |
| UI Boundary Architecture | アプリケーション実装 | この画面の責務をどこで切り、状態をどこに置くか |

この1点から、以下がすべて導ける。第5章はこれを比較の起点に置く。

- Atomic Design が状態所有を扱わないのは、**扱えないから**(ライブラリの部品は、使う側のアプリの状態を知らない)。見落としではなく前提
- `Bridge` に対応物がないのも同じ理由(機能の連動はアプリ固有の事情)
- Templates / Pages が対応しないのも同じ(ライブラリからアプリケーションへ手を伸ばしている部分にあたる)

**必ず添える注釈**: 重なっているのは `Part` / `Component` の帯だけ。

```text
コンポーネントライブラリの領分   アプリケーション実装の領分
Part / Component                 Island / Bridge / Scaffold
Atoms / Molecules                （Atomic Design に対応物なし）
```

UI Boundary Architecture もこの帯を含むため、**「Atomic Design はライブラリ専用、UI Boundary Architecture はアプリ専用」と切り分けると不正確**になる。帯の中では観点が2つ、帯の外では片方だけ、という関係で書く。

この境目は第7章の昇格規則(`Part` は共有から始めてよい / `Island` の共有は慎重に)と同じ線を引いている。相互リンク済み。

**第2段階 — 帯の中での直交。**

**Atomic Design は、UI Boundary Architecture の立場から見ると `Part` / `Component` の内側にある「大きさの目盛り」**、という位置づけを第5章へ追加した。

判定基準を状態の有無に変えたことで、2つの軸が直交した。

- UI Boundary Architecture の軸 — 状態を持つか
- Atomic Design の軸 — 何から組み立てられているか

Molecule であっても、状態を持てば `Component`、持たなければ `Part`。互いを制約しない。

**成り立つ範囲を必ず添える。** 5段階すべてが目盛りとして働くわけではない。

| Atomic Design | 目盛りとして使えるか |
| --- | --- |
| Atoms / Molecules | 使える |
| Organisms | 半分。状態と機能を持って独立するなら `Island` |
| Templates / Pages | 使えない。`Scaffold` の話 |

Organisms が境目になるのは、UI Boundary Architecture がそこで軸を切り替えている(要素の性質 → 機能の独立性)ため。

第8章「この手法が答えないこと」に挙げていた「どこまで細かくコンポーネントを分けるべきか」が、この整理で第5章へつながった。**一方が空けている場所に、もう一方が入る**という関係になっている。相互リンクを張った。

### C-069 [S5] 未対応 / 中 — `Bridge` を1ファイルで書くと Fast Refresh の規則に抵触する

**該当**(01-Boundaries.md「実装ではどう表現されるか」):
> **置く側と読む側の両方**を挙げます。`Bridge` を実装するとは、この2つを書くことです。

**不足している情報**: 置く側(Provider コンポーネント)と読む側(フック)を1つのファイルへ書くと、React の標準的な lint 規則 `react-refresh/only-export-components` に抵触すること。

**なぜ必要か**: 本文の指示どおり `Bridge` ごとに Provider とフックを1ファイルへ置いたところ、4つの `Bridge` すべてで警告が出た。コンポーネント以外を export しているファイルは Fast Refresh の対象から外れ、編集のたびに状態が失われる。回避するには `Bridge` を2ファイルに割る(Provider と、Context + フック)必要がある。

**追加すべき内容**: 対応表の直後に1段落。ファイル分割は `Bridge` の分割ではないこと、React では lint 規則の都合で Provider とフックを別ファイルに置く構成が一般的であること。

### C-070 [S5] 未対応 / 重大 — 「描画構造に現れない」が、`Bridge` の位置が持つ制約を隠している

**該当**(03-Structure.md「論理構造は描画構造ではない」):
> - `Bridge` は描画構造に現れません

**該当**(01-Boundaries.md「実装ではどう表現されるか」):
> Provider はコード上のノードとして書かれますが、余白も枠も生まないため、描画構造には現れません。

**不足している情報**: Provider は描画構造に現れなくても**コードの木の中に位置を持ち、その位置が「誰がその `Bridge` を読めるか」を決める**こと。とくに `Scaffold` が `Bridge` を読み書きする場合、Provider は `Scaffold` の状態より外側に来る。

**なぜ必要か**: 適用した画面では `Scaffold` 自身が `Bridge` の状態を書く必要があった。キーボード入力が表示中のレイヤーと押下キー(いずれも `Bridge`)を書き、ビューの切り替えが選択の固定(`Bridge`)を解除する。`Scaffold` が `Bridge` を読むには Provider の内側になければならず、結果として `Scaffold` は**Provider を重ねる外側**と**画面の状態と構成を持つ内側**の2つのコンポーネントへ割れた。

冒頭の並びは論理構造であって描画構造ではない、と第3章は述べている。しかしこの割れ方は描画構造の話ではなく、**論理的に上位のはずの `Scaffold` が、実装上は `Bridge` の内側に入る**という現象である。「描画構造に現れない」だけを読んだ読者は、Provider をどこに置くかは自由だと受け取り、ここで手が止まる。

**追加すべき内容**: 第3章の当該箇所に1段落。`Scaffold` が `Bridge` を読む場合(画面全体のキーボード操作、ビュー切替時の後始末など)、Provider は `Scaffold` の状態より外側に置くことになり、`Scaffold` が2つのコンポーネントに分かれること。これは論理構造の逆転ではなく、値を配る仕組みの制約であること。C-073 と根が同じ。

### C-071 [S5] 未対応 / 中 — `Bridge` を分割する基準はあるが、統合する基準がない

**該当**(01-Boundaries.md「Bridge を分割する合図」):
> **その `Bridge` を参照している `Island` の組み合わせが、状態ごとに違っているなら分割する。** これが判断の基準です。

**不足している情報**: 組み合わせが違う状態を、それでも1つの `Bridge` にまとめてよいのはどんなときか。

**なぜ必要か**: この基準を字句どおり適用すると `Bridge` が増えすぎる。適用した画面では共有状態が6つあり、参照する側の組み合わせは6通りすべて異なっていた。基準に従えば `Bridge` は6つになる。実際には意味のまとまり(選択・検索・レイヤー・押下)で4つへ寄せたが、**その判断の根拠は本文にない。**

分割の合図として挙げられている「関係のない複数の状態を持ち始めたら」は、逆から読めば「関係のある状態は同居してよい」だが明示されていない。また、組み合わせが違っても関係が深い状態(この画面では固定中の選択とホバー中の選択)を分けると、両方を読む側が2つの `Bridge` を参照することになり、かえって見通しが悪い。

**追加すべき内容**: 分割の合図の直後に、統合側の基準を1段落。「組み合わせが違っていても、同じ問いに答える状態(何が選ばれているか、何で絞り込んでいるか)は1つの `Bridge` にまとめてよい。この基準は更新境界を無用に広げないためのものであり、`Bridge` の数を増やすためのものではない。」

### C-073 [S5] 未対応 / 中 — 画面全体の入力を受ける処理の置き場所がない

**該当**: なし(該当箇所が存在しないことが指摘)

**不足している情報**: 画面全体にかかる入力(ウィンドウのキーボードイベント、ショートカット、フォーカス喪失の検知など)を受ける処理を、どの単位に置くか。

**なぜ必要か**: 適用した画面には、PC のキーボードを実機に見立てる入力処理があった。`window` の `keydown` / `keyup` / `blur` を購読し、**表示中のレイヤーと押下キー(`Bridge`)、プロファイルと Hypershift の固定(`Scaffold`)の4つを横断して書く。** 特定の `Island` の中で完結せず、描画も持たない。5つの単位のどれにも当てはまらない。
